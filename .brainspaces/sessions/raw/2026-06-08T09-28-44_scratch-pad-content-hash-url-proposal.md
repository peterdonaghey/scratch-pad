[AGENT]: I completely understand the need. Here's the full picture I've gathered:

## Current Flow

```
Agent → POST /api/url  { "md": "# long markdown..." }
     → API builds URL: https://scratch-pad-beryl.vercel.app/?md=%23+long+markdown...
     → Returns that URL ← the whole markdown is IN the URL
User → clicks URL → app reads ?md= param → renders it
```

The problem: the entire markdown is stuffed into `?md=` in the URL. The agent encodes it, the URL is massive, the user sees a wall of encoded text.

## What you asked about: "reversible content hash"

This is a key conceptual question. A **hash** (SHA-256, MD5, etc.) is **one-way** — you can't unfold it back into the original content. You'd need a lookup table (hash → content) stored somewhere. So hashing alone doesn't solve it — you need a store to look up against.

What actually exists is **compression** (e.g., [LZ-String](https://github.com/pieroxy/lz-string)), which is two-way: compress → shorter string → decompress → original. But the data is *still in the URL*, just smaller. For typical markdown (500–2000 chars), you'd get roughly 40–60% reduction. Better, but not clean short URLs.

## The fundamental constraint

The app is a static SPA with no backend storage. Currently the URL *is* the transport. If you want short URLs without the full markdown in them, something has to store the content server-side so the browser can fetch it by short ID.

## Options I see

**Option A: Vercel KV (minimal backend)** → My recommendation

Add Vercel's built-in Redis KV store. The API stores the markdown with a short nanoid key, returns `https://.../?id=abc123`. The frontend fetches content from a new `GET /api/content?id=abc123` endpoint when it sees `?id=` in the URL.

- **Pros:** Clean short URLs, agent sends one POST and gets a tiny URL back, persists for a reasonable TTL (e.g. 7 days), no localStorage trickery needed for sharing
- **Cons:** Adds `@vercel/kv` dependency, requires Vercel KV integration (one click in dashboard)
- **Total new code:** ~30 lines in a new `api/content.mjs` + ~10 lines changed in `api/url.mjs` + maybe 15 lines in `storage.ts`

**Option B: LZ-String compression in URL** (zero backend)

Compress the markdown with LZ-String into a compact URL-safe string. The URL becomes `https://.../?c=<compressed>` — shorter, but the content is still in the URL.

- **Pros:** Zero new infrastructure, no database, still works offline
- **Cons:** Not *short* URLs — just *shorter* ones. For a 3000-char doc, maybe a 1500-char URL. The agent still sends the full markdown to the POST endpoint.

**Option C: Both** — compress server-side + store in KV

Agent sends raw markdown to POST endpoint → API compresses+caches it → returns a short `?id=` URL. Frontend fetches via GET endpoint. Best of both worlds.

---

I'd go with **Option A** — it's the right tool for the job, Vercel KV is free on the hobby plan, and it keeps the URLs truly clean. Want me to build that out, or would you prefer the compression-only route to keep zero backend deps?

## Document Viewer — Scoped

### Current state

LocalStorage keys follow the pattern `scratch-pad-state` (unnamed) and `scratch-pad-state:<name>` (named sheets). Each stores `{ markdown, prose }`. There's currently **no way to discover** what you've saved — you have to know the name and type the URL.

### What it would do

A "My Sheets" panel — a slide-over (same pattern as the existing Styles panel) that lists all saved documents:

```

│ My Sheets              ✕   │
├─────────────────────────────┤

### Files to touch

| File | Change |
|------|--------|
| `src/storage.ts` | Add `listSavedSheets()` — reads all localStorage keys matching `scratch-pad-state*`, returns `[{ name, title, snippet, markdown, prose }]` with a derived title (first `# heading` or the sheet name) and a snippet (first ~100 chars). Optionally add a `savedAt` timestamp to `ScratchPadState` if we want last-modified info. |
| `src/types.ts` | Add `savedAt?: number` to `ScratchPadState` so we can show when it was last saved. |

| `src/index.css` | Styles for the sheet list items, card layout, truncation. |

### What each entry shows

- **Title** — the first `# Heading` found in the markdown, falling back to the sheet name, falling back to "Untitled"
- **Snippet** — first ~120 chars of plain-ish text (strip headings/markdown), truncated
- **Sheet name badge** — shown if different from the title
- **Delete** — removes from localStorage, refreshes the list

### Design constraints (keep it minimal)

- Same slide-over pattern as the Styles panel — no new routing needed
- No edit-in-place — click Open to navigate to `/<name>` (or `/` for unnamed)
- The unnamed sheet is always listed first as "Untitled" (unless it's the welcome markdown and never been edited → skip it)
- Delete shows a confirm prompt before removing

### What it wouldn't do

- No search, no sort, no multi-select, no bulk operations
- No cloud sync — localStorage only, same as the rest of the app
- No preview rendering inline — just text snippets to keep it light
